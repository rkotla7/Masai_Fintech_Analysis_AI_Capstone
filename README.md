# Paytm FinTech Analytics & AI Platform

A single end-to-end analytics, machine-learning, and AI-assisted advisory platform built around three Paytm-inspired financial verticals:

1. **Payments & Fraud Analytics** — transaction analytics, merchant operations, SQL fraud detection, reconciliation, and an executive dashboard.
2. **Credit Risk & Lending ML** — credit-default prediction, risk-based pricing, transaction anomaly detection, and model governance considerations.
3. **AI-Augmented FinTech Advisory & Blockchain Risk** — portfolio allocation using CAPM and portfolio variance, structured disclosure extraction, a multi-agent debate demo, DCF valuation, and a blockchain/crypto risk appendix.

All datasets are synthetic and deterministic. No real Paytm customer or transaction data is used.

## 3.6 Bias awareness and model recommendation

Even though gender and location are not explicitly present, variables such as employment type, income, and bureau score could act as correlated proxies for protected characteristics in a real deployment. A model can therefore produce disparate outcomes even when protected attributes are excluded from the feature set.

Particular care is required for thin-file applicants because a missing bureau score is not necessarily evidence of poor creditworthiness; it may simply indicate that the applicant is new to credit. The alternate-data features used by the model should therefore be monitored for disparate impact.

A recommended governance control is a maker-checker human review for declined or highly penalized thin-file applicants. Model performance should also be monitored after deployment using approval rates, default rates, calibration, and fairness metrics across appropriate protected groups. Thresholds and pricing policies should be periodically reviewed rather than allowing the model to operate as an unchallenged automated decision-maker.

### Final recommendation

**Logistic Regression should be preferred for the Paytm Postpaid deployment candidate.** It achieves higher accuracy (76% vs. 67%), precision (38.89% vs. 24%), recall (35% vs. 30%), F1 (36.84% vs. 26.67%), and substantially higher AUC (71.88% vs. 53.13%) than the Decision Tree on the identical test set. The Logistic Regression model therefore provides the stronger overall ranking and discrimination performance in this experiment. However, it should still undergo calibration, fairness testing, threshold optimization, and human-governance review before production use.

## 4.2 Portfolio advisory agent


The agent follows:

```text
THINK
  ↓
ACT
  ↓
OBSERVE → DECIDE
```

The allocation is prescribed by risk tolerance:

| Risk         | Allocation                     |
| ------------ | ------------------------------ |
| Conservative | PAYBOND / PAYGOLD / PAYRETAIL  |
| Moderate     | PAYRETAIL / PAYINFRA / PAYGOLD |
| Aggressive   | PAYTECH / PAYFIN / PAYINFRA    |

All allocations are equally weighted at 1/3 per security.

CAPM expected return is calculated using:

```text
E(R) = Rf + beta × (Rm − Rf)
```

Only beta is used. `analyst_expected_return` is deliberately not used in the CAPM calculation.

Portfolio variance uses pairwise correlation:

```text
rho = 0.3
```

Human escalation occurs when:

```text
portfolio standard deviation > 20%
```

## 4.5 DCF valuation

Run:

```bash

```

The DCF uses unlevered FCFF:

```text
FCFF =
EBIT × (1 − tax rate)
+ D&A
− CapEx
− ΔNWC
```

Illustrative assumptions include:

```text
EBIT = INR 120 crore
Tax rate = 25%
D&A = INR 30 crore
CapEx = INR 45 crore
ΔNWC = INR 10 crore
```

The resulting base FCFF is:

```text
INR 65 crore
```

The WACC uses CAPM cost of equity with PAYFIN's beta, an illustrative after-tax cost of debt, and a 70% equity / 30% debt capital structure.

Recorded results:

```text
Cost of equity: 15.10%
After-tax cost of debt: 7.125%
WACC: 12.7075%
Terminal growth: 5.50%
Enterprise Value: INR 1,353.75 crore
```

The 3×3 WACC/terminal-growth sensitivity table passes the required constraint. The worst-case difference between WACC and terminal growth is approximately:

```text
5.21 percentage points
```

which is above the required 1 percentage point minimum.

The EV/EBITDA cross-check gives:

```text
EBITDA = INR 150 crore
Multiple = 9.5x
Implied EV = INR 1,425 crore
```

The DCF value is approximately 5% below the EV/EBITDA estimate. The difference is reasonable for an illustrative exercise because DCF is sensitive to the explicit growth, discount-rate, and terminal-value assumptions, whereas the multiple method applies a market-based valuation multiple to EBITDA.

# 5. Blockchain / Crypto Risk Appendix

The written appendix is:

```text
ai_advisory_blockchain/blockchain_risk_note.md
```

It addresses:

1. Stablecoin type and DeFi/DAO governance risk.
2. Crypto as an asset class and a specific retail allocation recommendation.
3. T.A.N.G. social-engineering risks and corresponding bank-side defenses.

The recommendation is a maximum crypto allocation of approximately **2–3% for eligible retail investors**, with **0% for Conservative profiles and very short investment horizons**. This small capped allocation is intended to limit portfolio damage from crypto's high volatility, heavy-tailed returns, survivorship bias, uncertain intrinsic-value basis, transaction/custody costs, and unstable diversification benefits.

For the T.A.N.G. framework, the two emphasized vectors are:

* **Authority** — mitigated through real-time transaction-intent screening and stronger confirmation for suspicious collect/payment requests.
* **Need** — mitigated through real-time controls against upfront "processing fee" payments outside the legitimate lending workflow.

# 6. Key Design Decisions

## Payments

* Synthetic transaction data is generated using the prescribed random seed of 42.
* SQLite is used as the normalized relational store.
* Set operations identify missing/extra transactions while `pd.merge` performs pairwise comparisons.
* The reconciliation headline metric requires both amount and status to match.
* Chargeback ratios are count-based rather than amount-based.
* Excel uses fixed-range VLOOKUP, HLOOKUP, nested IF/AND, and pivot-table functionality.
* Dashboard outputs are generated as static images so no live BI dependency is required.

## Credit Risk

* Stratified train/test splitting preserves the default-class proportion.
* Thin-file status is derived directly from the raw missing bureau score.
* Bureau-score imputation uses the training-set median only.
* StandardScaler is fitted only on training data.
* Logistic Regression and Decision Tree use the same train/test split.
* Logistic Regression probabilities drive the illustrative risk-pricing tiers.
* Isolation Forest contamination matches the seeded anomaly proportion.

## Advisory

* Allocation is dictated by the prescribed risk-tolerance lookup table.
* CAPM uses beta only and intentionally ignores `analyst_expected_return`.
* Portfolio variance assumes pairwise correlation of 0.3.
* Volatility above 20% triggers human escalation.
* Mock LLM mode is deterministic and keyless.
* Disclosure extraction uses deterministic keyword/regex logic in the graded baseline.
* The DCF uses unlevered FCFF and an illustrative WACC/capital structure.
* Terminal growth is deliberately conservative enough to satisfy the sensitivity-grid constraint.
