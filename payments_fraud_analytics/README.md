# Part 1 — Payments & Fraud Analytics

Paytm vertical: Payments (UPI / Wallet / QR merchant payments).

## Setup
From the repo root: `pip install -r ../requirements.txt` (or the root `requirements.txt` if
you're already in the repo root).

## Run order
```bash
cd payments_fraud_analytics          # must run from this folder — relative paths
python generate_data.py              # regenerates merchants.csv, users.csv, ledger.csv, gateway_export.csv (seed 42)
python reconcile.py                  # Part C — reconciliation, writes recon_*.csv
python dashboards.py                 # Part D — writes dashboard_1..4_*.png
```
`merchant_workbook.xlsx` (Part A) is a committed Excel deliverable, opened directly in
Excel/Google Sheets/LibreOffice — it is not regenerated by a script.
`paytm_payments.db` (Part B) is the committed SQLite database; `fraud_pattern_detection_queries.sql`
contains all 7 queries with their recorded output.

## Design decisions

- **VLOOKUP/HLOOKUP:** merchant lookups use a fixed absolute range (`merchants_data!$A:$D`)
  wrapped in `IFERROR` to show "Merchant not found" for any unmatched `merchant_id`. The HLOOKUP
  demonstration uses an illustrative MDR-style fee table: UPI 0.4%, Wallet 0.6%, Card 1.8%,
  Netbanking 1.0% — chosen to reflect the real-world ordering (card acquiring costs more than UPI)
  without claiming to be Paytm's actual pricing.
- **Classification rule:** `IF(AND(daily_merchant_total_inr > 5000, region <> "East"), "High-Value
  Merchant Day", "Normal Day")`, exactly as prescribed in the brief, fed by a `GETPIVOTDATA`
  reference into the daily-total pivot.
- **Burner-account query boundary:** `0 <= (transaction_time - signup_date) < 30` days, computed
  via `julianday()` differences in SQLite, to make the "never negative, never ≥30" rule
  unambiguous. Surfaces all 15 seeded rows.
- **Velocity-attack query:** groups by `user_id` and a floored 10-minute bucket
  (`strftime` truncated to the 10-minute mark), `HAVING COUNT(*) >= 3`. Surfaces all 8 seeded
  clusters as distinct qualifying groups.
- **Reconciliation:** set differences on `transaction_id` for missing-in-gateway / missing-in-ledger,
  and `pd.merge` on the common IDs for amount/status mismatches. Measured discrepancy rates on the
  committed CSVs: ~4.9% missing-in-gateway, ~1.8% missing-in-ledger, ~2.9% amount mismatches, ~1.7%
  status mismatches — consistent with the ~5%/2%/3%/2% injection rates in `generate_data.py`.
- **Dashboard scorecards** use the exact definitions specified in the brief: `match_rate` requires
  both identical `amount_inr` AND identical `status` between ledger and gateway; `chargeback_ratio`
  is count-based (chargebacks ÷ all transactions), both platform-wide (headline) and per-merchant
  (details-layer high-risk flag, threshold >1%).
